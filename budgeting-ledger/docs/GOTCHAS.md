# Gotchas

Non-obvious constraints, workarounds, and ordering dependencies that aren't visible from a function's signature or a casual read. Read the relevant section before touching that area — these are things a past change already got wrong once, or will silently misbehave if you "clean up" the workaround without knowing why it's there. For schema/API detail see [TECHNICAL.md](./TECHNICAL.md); for product behavior see [FUNCTIONAL.md](./FUNCTIONAL.md); for a per-screen manual test pass see [MANUAL_TESTING.md](./MANUAL_TESTING.md).

## Sync (Google Sheets)

- **Foreign transactions are deduped by `ownerKey + date + amount`, not by a stable id** (`transactionRepository.upsertForeignTransaction`/`deleteForeignBySyncKey`, `database/repositories/transactionRepository.ts:167,190-195`). If a foreign owner logs two transactions with the same amount on the same date (e.g. two identical coffees), the second upsert silently overwrites the first row, and a delete meant for one can delete the other. There's also a **vestigial `CREATE UNIQUE INDEX idx_transactions_foreign_key ON transactions(ownerKey, note)`** (`transactionRepository.ts:159-161`) created on every foreign upsert that the actual matching query never uses (it filters on `date`+`amount`, not `note`) — leftover from an abandoned design; don't assume it enforces anything.
- **A transaction is treated as a sync "deleted marker" purely by `note === '(deleted)'`** (`services/syncService.ts:699`), checked *before* the real "Deleted At" column. A genuine user note of literally `(deleted)` means that row is never pulled/updated again for any other owner.
- **The per-device `ownerKey` is a random UUID with no recovery path** (`services/settingsService.ts:129-138`). Reinstalling the app, clearing app data, or moving to a new device generates a *new* owner key — all previously-synced "own" rows in the sheet now look foreign, get pulled back as **read-only**, and continued syncing starts appending duplicates under the new key. There's no merge/migration for this.
- **Amounts round-trip through a comma decimal separator** (`services/syncService.ts:57`, parsed back in `services/transactionService.ts:~703`) — written as `String(amount).replace('.', ',')`. This assumes the destination Google Sheet's locale uses comma-decimal formatting; a period-decimal sheet locale can make `USER_ENTERED` values parse differently than intended.
- **`categoryRepository.getOrCreateForeignCategory` matches with no `ownerKey` filter at all** (`database/repositories/categoryRepository.ts:76-90`) — purely `LOWER(TRIM(name)) = ? AND TRIM(emoji) = ?` across the whole table. A foreign transaction whose category happens to match one of your own categories (very likely for the seeded defaults, e.g. "🍎 Groceries") silently attaches to *your* category row instead of creating a separate foreign one; two different foreign owners with the same name+emoji collide into one shared row.
- **Category/budget sync has no deletion tracking** (`services/categorySyncService.ts`) — unlike transactions, there's no tombstone table, so deleting a category locally never removes it from the sheet, and `importCategories` recreates it forever if another device still has it. `exportCategories` also issues one `PUT` per changed category in a serial loop (`:130-135`) rather than a single batch call — slower and more exposed to 429s with many categories.
- **Auto-sync has no catch-up** (`services/autoSyncService.ts:17-26`) — it only fires once the device clock reads ≥2 AM local *and* the stored "last run day" differs from today. If the app is never foregrounded after 2 AM on a given day, that day's sync is skipped entirely; a timezone change (travel) can also skip or double-run a day.
- **The background task handler is registered by import side-effect** (`services/autoSyncService.ts:107-118`, `TaskManager.defineTask` at module top level) — this only works because `app/_layout.tsx` imports `autoSyncService` at startup. Make that import lazy/dynamic/code-split and the OS-triggered background run silently no-ops with no error.
- **Access tokens refresh 60 seconds before expiry, not at expiry** (`services/syncService.ts:77`) — keep that margin if you touch the expiry math, or near-expiry calls can still hit a 401 mid-flight.
- **Re-auth prompting is throttled to once per 10 minutes** (`app/sync-settings.tsx:209-237`, `lastPromptAtRef`, on `AppState` "active"). Remove the throttle and every foreground with a missing/expired token immediately pops the Google OAuth browser.
- **Google OAuth is explicitly disabled in Expo Go** (`app/sync-settings.tsx:263-269`) because the `exp://` redirect URI is rejected by Google — only works from a dev/preview build. Android also has a manually-constructed `redirectUri` (`:90-98`) that diverges from the default used on iOS.

## Database

- **`getBudgetHealthData` compares raw date-only strings (`t.date >= ? AND t.date <= ?`) instead of the `substr(date,1,10)` pattern used everywhere else** (`services/budgetService.ts:64-67` vs. e.g. `database/repositories/transactionRepository.ts`'s date-range queries). Since `date` is stored as a full ISO datetime, a transaction on the *last day* of a period (`"...T23:59:00.000Z"`) sorts lexicographically **greater than** the plain end-date string, so Budget Health silently undercounts it even though History/Reports (which use `substr`) count it correctly. Don't copy this pattern elsewhere — copy the `substr(...)` form instead.
- **The `budgets` table is dropped and recreated if a legacy `period` column is ever detected** (`database/schema.ts:66-70`), discarding existing rows. Intentional one-time cleanup for pre-existing installs; don't reuse "drop on detect" for a column whose data you actually want to keep.
- **Every new column must be added via the `PRAGMA table_info`-gated `ALTER TABLE ADD COLUMN` pattern** (`database/schema.ts:80-99`) — this runs on *every* app start, not just after an upgrade, and `ALTER TABLE ADD COLUMN` errors if the column already exists.
- **`DEFAULT CURRENT_TIMESTAMP` produces a non-ISO string** (`"YYYY-MM-DD HH:MM:SS"`, space-separated, no `Z`) that some JS engines can misinterpret as local time. `services/transactionService.ts`'s `toIsoDate` exists specifically to normalize this — any new code path reading a raw `updatedAt`/`createdAt` must go through it (or set the timestamp explicitly via `new Date().toISOString()`, as `transactionRepository.create`/`update` already do).
- **Deleting a transaction must go through `transactionService.deleteTransaction`**, which wraps the delete + tombstone insert in a manual `BEGIN/COMMIT/ROLLBACK` (`:54-64`). Calling `transactionRepository.delete()` directly skips the tombstone — nothing errors, but the deletion never propagates to the Google Sheet.
- **`budgetRepository.upsert` is `INSERT OR REPLACE`**, which SQLite implements as delete+insert — a budget row's autoincrement `id` changes on every amount update even though `categoryId` doesn't (harmless today, nothing joins on `budgets.id`, but a trap if that changes). `budgetService.saveBudgets` also does `deleteAll()` then loops inserting with **no wrapping transaction** — a crash mid-loop leaves budgets partially wiped.

## UI / Animation

- **`SpendingBarChart`'s remount `key` in `app/reports.tsx`** encodes year/month/`donutType`/`selectedCategoryId` specifically so `react-native-gifted-charts` fully remounts instead of rendering with stale data on a filter change.
- **`CalculatorKeypad`'s slide animation is gated behind a `hasLaidOut` ref** (`components/ui/CalculatorKeypad.tsx:44-45,61-62,167-179`) and skipped until the first `onLayout` measures the real sheet height; removing that gate causes a visible jump/flash on mount.
- **`manage-categories.tsx`'s modal uses a different re-open pattern than `CalculatorKeypad`** — `openModal()` manually resets `translateY`/`backdropOpacity` *before* setting `modalVisible(true)`, rather than gating on a "has laid out" ref. Any new call site that flips `modalVisible` directly (bypassing `openModal()`) skips the reset and the slide-in plays from the wrong position or not at all.
- **`calcHeight` in `add.tsx`/`bill-splitter.tsx` lags one render behind the real keypad height** — it's reported asynchronously via `CalculatorKeypad`'s `onHeightChange` (fired from its own `onLayout`), so scroll-content padding uses a fallback until that first callback fires.
- **Three magic `setTimeout(..., 300)` calls** (`app/add.tsx:257`, `app/bill-splitter.tsx:116,135-138`, `app/budgets.tsx:72-75`) delay focusing an input / opening the calculator until *after* a modal's close animation finishes. They're tied to that modal's animation duration — changing a modal's timing elsewhere without updating these can make the calculator open underneath the still-closing modal, or the keyboard fail to appear.
- **`bill-splitter.tsx`'s `calculatorTarget: 'total' | number`** treats category index `0` as valid but falsy — all current checks correctly use `=== 'total'`/`!== 'total'`; a truthy-style check (`if (calculatorTarget)`) would misidentify the first split as the total.
- **`getMaxPercentageForIndex`** (`app/bill-splitter.tsx:85-101`) deliberately computes `Math.max(currentAmount, total - otherAmounts)` so the slider's max doesn't shrink mid-drag and clamp/jump the thumb as `splits` state updates on every tick.

## Theme

- **`ThemeProvider`'s initial color scheme is read via a synchronous `db.getFirstSync` call inside a lazy `useState` initializer** (`providers/ThemeProvider.tsx:13-20,48`). This only works because `app/_layout.tsx` gates all rendering on `dbReady`. Mount `ThemeProvider` before the DB is ready and `getStoredColorScheme` throws inside `requireDb()`, is silently swallowed by its `try/catch`, and the app falls back to the system color scheme with no visible error.
- **The system-scheme fallback defaults to `'dark'` for anything that isn't exactly `'light'`** (`providers/ThemeProvider.tsx:10-11`), including `null`/no-preference — not a symmetric light/dark default.
- **`theme/styles.ts` re-exports a legacy static `colors`/`shadows`/`gradients` frozen to the dark palette at module load**, alongside the real theme-reactive `useSharedStyles()` hook. All current screens correctly use `useSharedStyles()`; importing the static tokens directly would silently ignore the light/dark toggle.

## Date math (`utils/monthUtils.ts`)

- **`getCurrentMonthEnd` relies on JS `Date`'s day-index underflow** — `new Date(nextYear, nextMonth, monthStartDay - 1)` (`:57`): passing day `0` (when `monthStartDay` is 1) automatically yields the last day of the *previous* month. This is the entire mechanism for "day before the next period starts"; clamping the day argument to `>= 1` would break month-end specifically when `monthStartDay === 1`.
- **`getMonthPeriods` relies on the same overflow going the other direction** (`:88`, `new Date(py, pm - 1, pd + 1)`) to roll into the next calendar month.
- **All date-only strings here are built from local `getFullYear()/getMonth()/getDate()`, never UTC** (`toLocalDateString`, `:5-10`; `app/history.tsx:100-104` comments this explicitly). Introducing a UTC-based date-only string anywhere in this pipeline shifts the computed period boundary by a day for users west of UTC in the evening (or east of UTC near midnight).
- **`monthStartDay` is hard-capped to 1–28** (`services/settingsService.ts:41-50`) specifically so it always exists in every calendar month (including non-leap February) — the rollover math above depends on that guarantee; don't relax the cap without re-deriving it.

## Build / security config

- **`withBackupRules` (`app.config.js:41-56`) is the only thing that actually writes the Android backup-exclusion XML content** — `expo-secure-store`'s own config plugin only sets the manifest attributes pointing at `config/android/*.xml`, it never writes their contents. If this plugin or those XML files are ever removed/renamed, the dangerous failure mode isn't a build error — it's the manifest pointing at rules that no longer exclude the SecureStore-held SQLCipher key from Android's auto-backup, silently undermining encryption-at-rest.
